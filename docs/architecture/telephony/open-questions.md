> لطفاً در پاسخ‌ها **هیچ گذرواژه، کلید یا توکنی** ننویسید. اسرار هنگام پیاده‌سازی مستقیم در صفحه تنظیمات (رمزشده) وارد می‌شوند.

## ۰. فهرست جداگانه موارد نامشخص فنی

هیچ‌یک از موارد زیر در مخزن یا مستندات آن ثبت نشده است. طراحی برای هر مورد مسیر جایگزین دارد و هیچ‌کدام قطعی فرض نشده است (تصمیم D9).

### ۰.۱ نسخه Issabel و Asterisk

| نامشخص | اثر بر طراحی | روش رفع |
|---|---|---|
| نسخه Issabel (۴ یا ۵ یا دیگر) و بسته‌های نصب‌شده | وجود و رفتار رابط مدیریتی؛ امکان فاز ۴ | A1؛ کشف خودکار در فاز ۱ (فقط خواندن) |
| نسخه Asterisk | نام رویدادهای AMI (`DialBegin`/`BridgeEnter` از Asterisk 12 به بعد در برابر `Dial`/`Bridge` در نسخه‌های قدیمی‌تر) و ستون‌های CDR | A2؛ پاسخ `CoreSettings` در AMI |
| یک یا چند سرور، خوشه، شعبه | مقدار `pbx_key` و تعداد اتصال‌ها | A4 |
| منطقه زمانی و NTP | درستی زمان تماس‌ها | A7 |

| Context داخلی‌ها برای Originate | اعمال درست Outbound Routes و محدودیت‌ها | E4 |

### ۰.۳ رابط مدیریتی

| نامشخص | اثر بر طراحی | روش رفع |
|---|---|---|
| نصب و فعال بودن REST API مدیریتی Issabel (`/pbxapi`) روی سرور واقعی | تنها مسیر رسمی شناخته‌شده برای تغییر داخلی‌ها؛ بدون آن فاز ۴ فقط تیکت دستی است | B3؛ راهنمای Issabel آن را معرفی می‌کند ولی نسخه ارائه را نمی‌گوید و خود را ممکن است ناقص بداند ([منبع](https://ccmanual.issabel.com/en/api/issabel-api.html)) |
| پوشش API (داخلی، گروه زنگ، صف، مسیر) و قالب دقیق ورودی و خروجی | دامنه فاز ۴ و ۵ | آزمون روی سرور آزمایشی |
| رفتار اعمال پیکربندی (Reload خودکار) و اثر آن بر تماس‌های جاری | زمان‌بندی اعمال تغییرات | B6 |
| روش رسمی دیگر (Bulk Handler/CSV) و مجاز بودن استفاده از سمت سرور | مسیر جایگزین | B5 |
